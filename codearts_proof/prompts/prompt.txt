提示词1: 
    /plan
    角色：资深产品经理 / FDE，我是客户。
    输入：./README.md（缺失就先问我），可参考 ./project/docs/、原型、竞品。
    流程：
    0. 先建立一个临时branch, 我们在确认PRD稳定之后会删除这个临时的branch。(远程和本地)
    1. 先复述你的理解（≤300字）+ 列出3-5个关键不确定点。
    2. 使用 AskUserQuestionTool 或类似提问工具与我交互，不要只在正文里列问题等我回答。每轮≤3题，带选项+“其他”，标 [必答]/[可选]，别问 README 里已有的。
    3. 每轮问答后立即更新 PRD.md，并给我“本轮变更摘要”。
    4. 退出条件：目标用户/核心场景/MVP范围/成功指标/非目标 均明确，未决≤3条 → 输出“PRD初稿完成，请审阅”。
    5. PRD中必须有严谨格式的 "用户故事" (I am ... I want ... so that ... (不一定是英文, 中文也行))
    产出：./project/docs/Analysis/PRD.md
    结构：背景问题 / 用户画像 / 场景 / 功能范围(MVP-迭代-不做) / 成功指标 / 约束假设 / 风险依赖 / 待确认 / 变更记录。
    资产：如需绘制图表，图表文件统一存放在 ./project/docs/Analysis/assets/ 目录下，并在 PRD.md 中通过相对路径引用。
    约束：不编造需求；不确定标 [假设]/[待确认]；不写技术方案；术语一致；我前后矛盾时指出并让我裁决。

提示词2: 
    /plan
    角色：资深软件/硬件架构师或技术负责人，我是客户兼 PRD 负责人。
    输入：./project/docs/Analysis/PRD.md（缺失或与 README 冲突先问我），可参考代码库、硬件约束、部署环境。
    流程：
    0. 先建立一个临时branch, 我们在确认SPEC稳定之后会删除这个临时的branch。(远程和本地)
    1. 先输出“PRD→SPEC 映射表”+ 3-5个关键技术不确定点。
    2. 使用 AskUserQuestionTool 或类似提问工具与我交互，不要只在正文里列问题等我回答。每轮≤3题，按阻塞程度排序，优先问性能/兼容/部署/成本/合规，带候选方案+权衡+“其他”。
    3. 每轮问答后立即更新 SPEC.md，并给我“本轮变更摘要”。
    4. 退出条件：系统边界/模块/接口/数据模型/非功能指标均明确，每条 PRD 需求都有技术落点或标注“本版本不实现”，未决≤3条 → 输出“SPEC初稿完成，请审阅”。
    产出：./project/docs/Analysis/SPEC.md
    结构：概述与PRD对应 / 架构 / 模块职责 / 接口契约 / 数据模型 / 非功能 / 依赖 / 部署运维 / 风险与被否决方案 / 待确认 / 变更记录。
    资产：架构图、流程图、ER图等图表统一存放在 ./project/docs/Analysis/assets/ 目录下，并在 SPEC.md 中以相对路径引用。
    约束：不发明 PRD 外的业务需求；选型必须给“理由+被否方案+否决理由”；不确定标 [假设]/[待确认]；术语与 PRD 一致；区分“本版本”与“未来演进”。

提示词3:
    $project-spec-workflow
    角色：规格工作流负责人，我是需求提出者和最终决策人。
    输入：我的具体开发/缺陷/探索任务；读取仓库适用的 AGENTS.md、README、开发规范、相关 PRD/SPEC/架构文档、对应 Specification 文档组和实现代码。
    流程：
    0. 检查当前分支、工作区和最近 git log；保留已有改动，遵循仓库提交规范。
    1. 根据风险选择轻量、标准、跨边界/高风险、缺陷或原型路径；先复述目标、范围和不确定项。
    2. 全量阅读本次相关的 Specification 文档组及其上游权威文档，核对 proposal.md、spec.md、design.md、tasks.md 之间的表述、术语、状态和引用，避免重复定义或相互矛盾。
    3. 在现有服务/领域文档组中更新对应文件；按需维护稳定 REQ-xx、AC-xx.n、T-xx 追踪。没有技术决策变化时不强行扩写 design.md。
    4. 不为单次任务新建 changes 目录或重复复制已有规格；Git 分支、提交和 PR 记录历史。没有合适的文档组时，先检查仓库约定再决定是否初始化。
    5. 只对阻塞范围、安全、兼容、数据或产品承诺的问题向我提问；非阻塞未知明确标注 [假设]/[待确认] 并安排验证。
    6. 若任务要求实现，按 tasks.md 分步实施，执行适用验收并记录真实证据；区分规划目标、代码状态和实机/运行验证，不声称未执行的检查通过。
    7. 完成前运行规格组结构校验、检查文档链接和 git diff；按仓库提交规范提交，除非我明确要求，否则不要推送。
    产出：更新后的规格文档及必要实现；报告涉及的文档/代码、验收结果、未执行检查、风险和提交号。
    约束：以仓库事实来源和本 Skill 为准；保持单一事实来源；不虚构决策或证据；不覆盖无关工作区改动；轻量任务不强制生成完整文档链。
