# 变更提案：云哨 Spec 工作流 Skill 完善

> 状态：已完成<br>
> 路径：标准功能<br>
> 负责人：项目开发者与代码助手<br>
> 相关基线：`project/docs/Specification/WORKFLOW.md`、`README.md`、`COMPARISON.md`；`codearts_proof/skills/project-spec-workflow/`

## 背景与问题

现有 Skill 指向旧的单次变更文档路径，没有脚本化创建或检查能力，也没有充分体现仓库按服务/领域组织持久规格组的实际范式。容易令 Agent 重复建文档目录、重复抄写基线，或只生成任务计划而遗漏需求追踪和验收证据。

## 目标与成功观察

- Skill 描述风险分级、项目事实来源、功能/缺陷/原型路径、一致性评审、实现跟踪和验收回写。
- 使用与项目模板配套的脚本初始化新的领域规格组，并结构化检查需求、验收条件和任务引用。
- 文档说明以 Git 分支、提交和 PR 维护每次修改的历史。

## 范围

### 本次包含

- 重写 `project-spec-workflow` Skill 的入口指引并保持自动发现。
- 添加标准库 Python 脚本：领域组初始化和规格组一致性检查。
- 在 `project/docs/Specification/` 初始化本 Skill 的文档组，并同步目录说明、项目工作流和方法比较。

### 本次不包含 / 保持不变

- 不更改云哨产品行为、服务合同或实现代码。
- 不安装或引入 Spec Kit、OpenSpec、Kiro、BMad 等工具依赖。
- 不重写用户已有的服务规格组和工作区改动。

## 现状依据与约束

- 仓库当前工作区按服务/领域组织 `proposal.md`、`spec.md`、`design.md`、`tasks.md`。
- `project/docs/Specification/WORKFLOW.md` 是该项目规格约定的权威说明。
- 外部方法只用于提炼澄清、一致性分析、增量同步、功能/缺陷分流和单一事实来源等有用做法。
- 初始化脚本必须拒绝覆盖已有领域组；验证脚本只报告结构一致性，不能代替设计评审或运行验收。

## 备选方案与建议

| 方案 | 收益 | 成本/风险 |
|---|---|---|
| 直接复制某个外部框架 | 流程术语和命令现成 | 会重复云哨的基线结构并引入不需要的生命周期 |
| 按仓库结构蒸馏工作流并提供轻量脚本 | 贴合当前文档组，脚本无第三方依赖 | 需维护项目模板和验证规则 |

建议：采用第二种方案。

## 影响面、依赖与风险

- 影响 Skill、规格模板和项目工作流说明；不改产品源码。
- Python 标准库即可运行；Skill 脚本验证边界在 Markdown 结构及 REQ/AC/T ID 链接。
- 后续如调整文档组模板，应同步更新初始化脚本和验证器。
