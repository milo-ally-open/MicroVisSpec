# 行为规格：云哨 Spec 工作流 Skill

> 关联提案：[proposal.md](proposal.md)<br>
> 来源：仓库现有 Specification 文档组与用户确立的 Git 历史约定

## 范围和术语

本规格定义项目 Spec Skill 如何指导文档创建、评审、实现跟踪和验收；不改变产品行为。领域组指 `project/docs/Specification/` 下按服务或领域组织的持久文档组。

## 需求与验收条件

### REQ-01：按风险控制文档深度

**需求**：当 Agent 处理功能、缺陷、跨边界工作或原型时，Skill 应指导其选择最小充分的文档深度，并保留与风险有关的澄清和验收要求。

**验收条件**

- **AC-01.1** 给定一个低风险局部调整，Skill 指导记录目标、范围、不变项和验收，不强制生成完整文档链。
- **AC-01.2** 给定跨服务、账号授权、数据迁移或设备兼容工作，Skill 要求记录受影响需求、模块、任务、验收及相关安全/兼容/回滚事项。
- **AC-01.3** 给定根因未证实的缺陷或未解技术风险的原型，Skill 将事实与假设区分，并指导记录复现或停止/成功判据。

### REQ-02：在既有领域组维护文档

**需求**：Skill 和初始化脚本应将持久规格放在对应领域组中，并以 Git 跟踪历史。

**验收条件**

- **AC-02.1** 给定一个已有领域组，Skill 指导更新已有权威文件，不复制无关基线。
- **AC-02.2** 给定一个新领域，脚本从 Skill 模板创建所选模式需要的文档；目标目录存在时拒绝覆盖。
- **AC-02.3** 工作流说明将 Git 分支、提交和 PR 作为修改历史与评审记录。

### REQ-03：检查文档间追踪关系

**需求**：验证脚本应报告规格组缺件、未完成模板标记、重复或缺失 ID，以及任务与需求/验收条件的引用错误。

**验收条件**

- **AC-03.1** 给定含有缺失文档或未替换占位内容的规格组，脚本以非零状态退出并指出问题。
- **AC-03.2** 给定 REQ、AC 和 T 之间存在重复、悬空或未覆盖引用的规格组，脚本以非零状态报告对应 ID。
- **AC-03.3** 给定结构完整且 ID 互相对应的规格组，脚本返回成功并输出文档和条目计数。

### REQ-04：保持单一事实来源

**需求**：Skill 应将产品范围、研究证据、系统结构、跨服务合同和服务/领域合同分别指向其权威文档，并要求实现与规格一致。

**验收条件**

- **AC-04.1** 给定实现证据与规格有差异，Skill 要求判断是代码缺陷还是需求决策改变，并更新对应事实来源。
- **AC-04.2** 交付摘要应区分实际验证、未验证项、设备证据与模拟证据，不宣称未执行的检查通过。

## 不变项与兼容要求

- 保留现有服务和领域规格路径及其未提交改动。
- Skill 保持自动发现，不要求外部 Spec 工具或新增运行时依赖。
- 项目代码、部署、设备和产品合同不因本次工作发生变化。

## 数据处理和保留

无数据或运行时状态变更。

## 明确不做

- 不创建独立的每任务规格目录。
- 不用脚本判断产品决策是否正确，也不把文档检查当作代码验收。
