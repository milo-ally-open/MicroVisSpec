# 教室行为检测首发场景范围提案

> 状态：实现进行中（模型产物已入库；板端加载与运行验收待执行；告警规则产品默认已确认）<br>
> 路径：跨边界/高风险<br>
> 负责人：平台与边缘端<br>
> 相关产品需求：[PRD](../../Analysis/PRD.md) §1–§7；[总技术规格](../../Analysis/SPEC.md) §1、§2、§3；[系统架构](../../Design/STRUCTURE.md)

## 背景与问题

原首发场景写为消防通道占用。用户已明确将首发改为教室行为检测。仓库内课堂模型流程 [WORKFLOW.md](../../../preparation/model_classroom_behavior/WORKFLOW.md) 定义 YOLO11n、640 输入和 `hand-raising`、`reading`、`writing` 三类；PT、ONNX、Ascend 310B4 OM 已在 `preparation/model_classroom_behavior/` 入库，OM 哈希写入模型清单并核对。正式边缘插件及配置已编译，Atlas 实机模型加载和运行指标仍待验收。

## 目标与成功观察

- 在 Atlas 200I DK A2 上使用 Atlas 边缘运行时已验证并激活的课堂 OM 模型，处理授权 H.264 教室视频，并向设备服务报告运行状态。
- 视频可显示类别、边界框和置信度；三类告警规则初始全部关闭。
- 规则显式启用后，只有符合该类规则的行为生成云端异常事件；普通检测不进入告警与推送链路。
- Web/PWA 能管理设备和规则、查看授权视频、查询并处置生成的异常事件。
- 不把检测结果用于身份识别、跟踪、成绩或专注度判断。

## 范围

### 本次包含

- YOLO11n/640 活动模型的类别映射、推理状态与场景语义；模型包清单、哈希校验、芯片兼容、版本激活和回滚由 [Atlas 边缘运行时规格](../atlas_edge_runtime/spec.md) 唯一负责。
- Atlas 边缘运行时、设备身份、心跳、配置同步、MQTT 事件上报、幂等本地缓存与状态回报。
- `hand-raising`、`reading`、`writing` 三类可配置规则；每类独立启用、置信度阈值、持续条件和事件等级；默认全部关闭。
- 端云的事件/证据、媒体预览、设备及算法状态接口，以及 Web/PWA 配置和展示。

### 本次不包含 / 保持不变

- 消防通道场景、MCP 工具、原生移动端。
- 学生身份识别、跨帧身份跟踪、学生评分、专注度或课堂纪律评价。
- 采集或云端存储未命中告警规则的检测记录；仅在已授权的实时画面中展示检测叠加层。
- 将 `.pt` 或 `.onnx` 作为 Atlas 在线推理格式；板端目标格式为适配 Atlas 200I DK A2 的 `.om`。

## 现状依据与约束

- 代码依据：`project/src/device_sides/atlas200idka2/` 包含 agent/model catalog 基础以及正在并入的 classroom-runtime/plugin/多模型配置；权重与转换产物位于 `project/preparation/model_classroom_behavior/`。本次实现需让正式 Atlas 产品构建直接包含推理和媒体模块。
- 用户已确认：首发场景教室行为检测；选择 `WORKFLOW.md` 中 YOLO11n/640 流程；所有告警规则默认关闭且可配置；权重已提供，先实现运行时和模型转换。
- 工程组织参考 [device_side_ax650](https://gitee.com/milo-ally-intern/manhole-cover-detection/tree/master/model_deployment/device_side_ax650) 的通用模型插件、manager/pipeline、逐流配置与独立告警规则；该项目运行在 AX650，Atlas 侧只沿用职责边界并实现 AscendCL/CANN 接口。
- Atlas 设备已核验为 200I DK A2 / Ascend 310B4，Ubuntu 22.04 aarch64，CANN 7.0.RC1；板上未安装 Go。优先使用现有 C++/AscendCL 路径；MQTT 客户端库、编码推流路径仍需在实现环境核验。
- 真实教室视频只能使用经授权的样例或录制；模型验收不能由模拟数据代替。

## 备选方案与建议

| 方案 | 收益 | 成本/风险 |
|---|---|---|
| 在现有课堂 C++/AscendCL Demo 上建立常驻边缘代理并消费 Atlas 运行时激活的模型包 | 复用现有后处理与 Atlas 运行路径；不要求板上安装 Go | 需要把 CLI 视频执行形态纳入服务生命周期、健康状态和 MQTT/本地缓存 |
| 在 Atlas 上单独部署 Go Agent 并由其调用推理程序 | 控制面与推理解耦 | 板上无 Go 工具链，需额外构建与分发 Go 二进制；增加进程接口 |

建议：复用 C++/AscendCL，边缘控制、模型运行、持久事件缓存分层；先完成可加载模型和可禁用规则，再接入后续提供的真实 OM 包。

## 影响面、依赖与风险

- 产品范围、PRD、全局 SPEC、边缘服务、device/event/media/push 五个云服务、Web/PWA、部署配置及模型数据处理。
- 依赖模型方交付与 `WORKFLOW.md` 一致的 YOLO11n/640 模型；转换生成目标板 OM 及 classes 顺序、SHA-256 和兼容信息。
- 需要校验 Atlas 的 RTSP 输入、叠加视频发布、MQTT 身份、HTTPS 证据上传以及断网恢复；当前尚无端到端实机证据。
- 模型激活失败时保留上一个有效版本；边缘服务回滚不删除缓存事件；课堂规则缺省关闭。
