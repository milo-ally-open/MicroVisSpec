# Spec 工作流

## 1. 选择文档深度

从最小充分的文档开始，按改动影响升级流程。目标目录始终是相关服务或领域的持久规格组；Git 分支、提交和 PR 负责修改历史。

| 路径 | 适用情况 | 必须留下的内容 |
|---|---|---|
| **轻量** | 局部、低风险、易回滚，且不改变接口、数据、安全边界或产品承诺 | 在对应 `proposal.md` 记录目标、范围、不变项和验收；实现后补验证结果 |
| **标准功能** | 新功能或可见行为变化，影响范围可控 | 更新 `proposal.md`、`spec.md`、必要时的 `design.md` 和 `tasks.md` |
| **跨边界/高风险** | 跨服务、身份隔离、消息一致性、数据迁移、媒体/设备协议、硬件资源、隐私安全、部署兼容或产品承诺变化 | 标准文档 + 完整 REQ/AC/T/证据追踪；写明安全、兼容、失败、回滚和运营影响 |
| **缺陷** | 实际行为违反现有合同或出现回归 | 记录环境、复现、实际/预期行为和影响；根因未证实则标假设；在 `spec.md` 增加回归验收 |
| **探索/原型** | 关键技术事实未知，先验证比直接实现成本低 | 写明问题、证据、成功/失败与停止条件、影响面和清理边界；结论回写后再决定是否实现 |

以下事项不能走轻量路径：账号数据隔离、公开或设备接口、数据库语义/迁移、跨服务重试/幂等、截图/视频/凭据等敏感数据、Atlas 200I DK A2 资源预算、PRD 范围或用户工作流变化。

## 2. 读取事实并澄清范围

1. 检查 `AGENTS.md`（如有）、README、`project/docs/WORKFLOW.md`、`RULES.md`，以及相关 PRD、Research、Design、全局 SPEC、领域组和源码。检查当前分支与工作区，保留用户已有改动。
2. 说明谁遇到什么问题、可观察结果、范围和非目标。不要仅凭旧规格声称功能已经实现。
3. 将证据、用户决定、建议和未知分开。产品选择标 `[待确认]`，未验证的技术判断标 `[假设]`，并给出影响、责任人或验证办法。
4. 若未知会改变产品承诺、授权、安全、数据、兼容或硬件边界，先解决它再做依赖决策的实现；非阻塞未知可保留并安排验证。

## 3. 在单一文档组内编写

### proposal.md：目标和范围

记录问题、现状证据、目标、包含/排除范围、影响面、依赖、方案选项和未决事项。缺陷补充复现与根因证据；原型补充停止条件与清理边界。`proposal.md` 记录同一工作范围的状态，不代表整个服务代码的完成度。

### spec.md：唯一行为合同

- 每条需求用稳定 `REQ-xx`，每个验收条件用 `AC-xx.n`；描述外部可观察行为和可执行/可观察的验证方式。
- 覆盖正常流程及本次相关的失败、边界、权限、数据保留和兼容情形。
- 将受影响的 PRD/全局合同映射到 REQ。只列本次有关内容，不复制整份上游文档。
- 跨账号边界覆盖允许与拒绝路径；异步消息说明重复、乱序、重试和幂等；设备/视频说明本次相关的断网、版本、编码和资源限制。
- REQ/AC 在 `spec.md` 定义一次；proposal、design、tasks 只能引用它们，不能改写成第二套合同。

### design.md：必要的实现决策

说明当前代码依据与目标边界，覆盖实际影响实现的接口/数据、状态和错误、安全、运行、兼容及恢复。已有全局/服务合同要引用章节；只描述本次差异。列出真实可行的替代方案和取舍；若没有新增技术选择，明确沿用的合同并说明无需另作设计。

### tasks.md：实施与证据

- 任务使用稳定 `T-xx`，每项可单独检查，写出目标模块、交付结果、依赖以及覆盖的 REQ/AC。
- 先处理会阻塞其他工作的合同、数据和接口，再安排依赖实现；只有读写边界清楚时才并行。
- 包含实现、配置/迁移、观测、回滚、验证和基线同步中适用的任务。
- 用 checkbox 记录实际进度；未知状态写“待核验”，只有有证据才标完成。实现偏差回到对应 spec/design 文件修订。

## 4. 编码前评审

- **轻量：** 目标、范围、不变项和验收清楚，风险可控。
- **标准：** 需求无冲突，失败路径与非目标可见，设计符合系统边界，任务能覆盖对应 REQ/AC，产品范围仍在 PRD 内。
- **跨边界/高风险：** 追踪矩阵覆盖受影响的 PRD/全局合同；明确授权、幂等、迁移、容量、隐私、兼容和恢复中适用的要求。会改变承诺或安全性的阻塞决策需由责任人确认后再实现。

按 `proposal → spec → design → tasks` 审阅。发现矛盾时修改拥有该事实的权威文件，不靠下游文档覆盖上游决策。文档结构验证只能发现 ID 与引用问题，不代表技术方案已批准。

## 5. 实现、验证和基线同步

1. 在仓库规定的分支和评审流程中实现；开始前确认工作区状态，不覆盖无关改动。
2. 按 `tasks.md` 分步工作，完成后更新任务状态。证据改变决策时先同步 proposal/spec/design，再继续依赖该决策的实现。
3. 依据 AC 执行适用验证，逐项记录命令/步骤、结果和证据。没有执行的检查不得标成通过。
4. 硬件/模型工作记录设备、固件/模型/数据版本及环境；模拟与实机证据明确区分。
5. 把长期有效结论写回唯一事实来源：产品范围写 PRD，外部事实写 Research，系统边界写 Design，跨服务合同写全局 SPEC，服务内合同写对应领域组。
6. `tasks.md` 和交付摘要应区分已验证、未验证、阻塞和风险。没有验收证据时，不标记已完成。

## 6. 原型路径

可先做短小、可丢弃的验证来回答具体未知，例如 Atlas 200I DK A2 编码/推理性能、WebRTC/HLS 兼容、MQTT 断网重传或新场景模型效果。开始前写清停止条件和副作用。取得结果后将证据写入 proposal 或 Research，并修订 spec/design 中的假设。继续则补正式验收与任务；停止则记录依据；证据不足则保留下一步和负责人。原型代码不会自动成为正式架构。

## 7. 交付说明

报告文档组路径、状态、实现范围、逐项验收证据、未执行检查、同步的基线文件和未解决风险。只有适用任务完成、验收证据记录、基线同步且未决项明确时，才标记工作完成。PR 合并、部署和用户验收仍按仓库流程处理。
