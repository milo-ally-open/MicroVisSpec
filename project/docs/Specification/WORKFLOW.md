# Spec 工作流

## 1. 先选合适的路径

每项改动先判断范围和风险，再选择所需文档深度。目录名用日期加简短英文 slug，例如 `2026-10-09-event-dedup`。涉及多个领域的需求先拆成可独立评审/验收的变更包，并标注依赖。

| 路径 | 适用情况 | 必需记录 |
|---|---|---|
| **轻量** | 单模块、局部、低风险、行为清楚、容易回滚的文案/样式/小修正；不改变 API、数据、安全边界或产品承诺 | 一页 `proposal.md`：背景、变更、不变项、验收点；实现后记录验证结果。无需复制完整模板 |
| **标准功能**（默认） | 新功能或可见行为变化，涉及一个或少量模块，接口与数据影响可控 | `proposal.md` + `spec.md` + `design.md`（确认无技术选择时注明“不需要”）+ `tasks.md` |
| **跨边界/高风险** | 跨服务、身份/账号隔离、事件一致性、数据库迁移、媒体/设备协议、硬件性能、隐私安全、部署兼容或产品范围变化 | 标准包 + REQ/AC/任务/验证追踪矩阵；明确回滚、兼容和运营影响；相关技术/产品责任人评审。超出 PRD 的产品决策需先确认并更新 PRD |
| **缺陷** | 现有行为不符合已写合同，或线上/联调出现回归 | `proposal.md` 使用缺陷字段：环境、复现、实际/期望、影响范围；`spec.md` 写修复后的行为和回归验收。根因未证实时标记假设，不把猜测写成结论 |
| **探索/原型** | 外部依赖、RK3588 实机、视频兼容、模型指标或新工具行为存在关键未知，先做小型验证更便宜 | 先写问题、成功/失败判据、范围与清理方式；允许先做可丢弃的 spike。结果记录在 proposal/Research，决定正式做后再生成行为规格和实现任务 |

以下情况不得走轻量路径：改动可能影响个人账号数据隔离；改变公开或设备侧接口；改变数据库语义/迁移；跨服务消息重试、去重或最终一致性；涉及截图、视频、凭据等敏感数据；改变 RK3588 资源预算或视频并发承诺；改变 PRD 范围、验收目标或用户工作流。

## 2. 调研和澄清

1. 阅读仓库 `AGENTS.md`（若存在）、README、`project/docs/WORKFLOW.md`、`RULES.md`、PRD、相关 Research/Design/SPEC、目标服务规格和对应源码。确认当前分支、工作区已有改动、实现状态和实际接口。不要用旧文档覆盖尚未提交的用户工作。
2. 把请求归纳为：用户/调用方、要解决的问题、可观察结果、明确不做的事、适用范围。已有 PRD 覆盖的产品事实不重复询问。
3. 标出证据、用户决定、建议和未知：事实引用文件/代码/来源；未确认的业务事项写 `[待确认]`；有依据但未经验证的技术判断写 `[假设]`；对方案有影响的未知说明负责人或验证办法。
4. 如果答案会改变产品范围、数据授权、安全边界、硬件承诺、外部兼容或不可逆迁移，先暂停依赖该答案的实现并请求责任人决定。其他未知可在规格里保留备选和默认假设继续非依赖工作。
5. 创建 `changes/<YYYY-MM-DD>-<slug>/`，从 `templates/` 复制需要的文件。轻量改动可以合并为一个 `proposal.md`，不要求空模板齐全。

## 3. 写规格包

### proposal.md：为什么改、改什么

记录背景、现状证据、目标、范围、非目标、依赖、影响面、方案选项、风险、未决问题，以及拟采用的规格和验收粒度。若是缺陷，另外给出复现条件、当前行为、预期行为、影响版本/设备以及可能原因（注明是否已证实）。提案不把技术方案伪装成产品需求。

### spec.md：改完后系统应如何表现

- 需求使用稳定 ID（如 `REQ-01`）；用角色故事、条件-行为-结果或 Given/When/Then 描述外部可观察行为。
- 每条需求有可判定的验收条件，包含主要路径、权限/失败/边界情形；验证方式应可执行或可观察。
- 写明不变行为、兼容性、数据保留与迁移要求，以及不在本次范围的事项。
- 跨账号边界默认验证正向和越权路径；异步消息说明重复、乱序、重试和幂等语义；设备/视频变更说明弱网、断线、编码/分辨率或资源约束中与本次相关的情况。
- 将本次实际影响的 PRD 用户故事/产品需求映射至一个或多个 REQ。若其中某项明确不在本次范围，记录为保持不变或后续处理；不得静默改变或删减相关产品承诺。普通功能包不要求重复列出整份 PRD 中与本次无关的需求；跨边界/高风险包要覆盖所有受影响的 PRD 与全局技术合同，并在规格中填写完整的需求-模块-任务-验收/证据追踪矩阵。

### design.md：用什么边界实现

说明现状和目标结构、受影响服务/页面/边缘进程、接口与字段、数据模型/迁移、状态/时序/错误处理、权限与日志、配置/部署、可观测性、兼容和回滚。只记录影响实现或评审的关键细节；无需重新抄写全局架构。列出至少一个真实可行的替代方案及取舍；没有实质技术决策时写明原因并跳过详细设计。

### tasks.md：按什么顺序交付

- 每项任务是能独立实现和检查的工作单元，写出目标文件/模块、交付结果、所依赖任务以及对应 REQ/AC。
- 先处理接口、迁移和跨服务合同，再安排依赖它们的实现；并行任务只在读写边界明确时标出。
- 单独列出实现、迁移/配置、观测、兼容与回滚、验证和文档回写工作；不要用“实现整个功能”作为唯一任务。
- 使用 checkbox 表示任务是否完成；任务进行中或受阻时，在任务行补充状态和阻塞原因。实现中发现规格有误时，先更新规格/设计，再继续依赖该决定的代码。

## 4. 评审门槛

在写代码前，按路径完成对应检查：

### 轻量改动

- 目标、范围、不变项、验收点清楚；改动低风险且可回滚。
- 若代码实现揭示了新增风险，升级为标准或跨边界路径。

### 标准功能

- 需求没有互相冲突；关键失败路径和非目标可见。
- 设计符合当前架构边界；任务依赖与 REQ/AC 对得上。
- 用户/产品范围仍在 PRD 内。所有阻塞实现或改变范围/安全/兼容承诺的未决项必须先解决；非阻塞项可以保留，但要有负责人或验证路径，并说明它为什么不阻止当前实现。

### 跨边界/高风险

- 需求追踪矩阵覆盖所有受影响 PRD/全局技术合同；账号授权、消息幂等、迁移、硬件/网络限制、日志隐私、回滚中适用的项目均有明确处理。
- 服务边界与数据所有权不被绕过；外部契约、版本兼容、失败和容量影响有明确结论。不会改变方案安全性、数据正确性、产品承诺或兼容边界的未知项，可以保留验证计划，但应在实现任务中标明，并在产生不可逆影响或部署前完成验证；阻塞这些边界的未知必须先解决。
- 责任人审阅变更包中的可见决策后才进入依赖性实现。不是每个常规改动都需要额外审批；这里的评审是为了先解决会改变产品承诺或系统安全/兼容边界的决定。

评审时按 `proposal → spec → design → tasks` 阅读：先判断做什么和为什么，再判断验收定义，再核对实现方案，最后确认任务只覆盖已批准范围。修订应回到拥有该事实的文件，不靠下游文档覆盖上游冲突。

## 5. 实现、验证和文档回写

1. 开始前检查工作区和目标分支，保留已有用户改动；一个变更包与其代码、相关验证记录在同一任务分支/PR 中，遵循仓库既有 Git 流程。
2. Agent 先读取本变更包及其链接基线；一次按任务清单实现一小组任务。完成一项就更新 checkbox；需求、设计、任务或代码发生偏差时记录原因并同步更新。
3. 依据仓库现有说明和本次变更风险执行相关验证。规格中的验证是交付定义；实际做过的检查与结果如实记录，没做的不要标成通过。
4. 验收按 AC 逐项给证据：自动化检查、接口结果、UI/设备实测、日志或可复现步骤。硬件/模型结果说明真实设备、固件/模型/数据版本和测试限制；模拟结果不能宣称为实机验收。
5. 完成前把长期有效结论回写唯一基线：产品范围改 PRD；外部证据改 Research；系统边界改 Design；跨服务合同改全局 SPEC；服务内合同改该服务规格。仅本次实现任务与历史决策留在变更包。
6. 实现通过验收、基线同步后，将状态设为 `已完成` 并移至 `changes/archive/<date>-<slug>/`。探索原型若决定继续，先将结论转为正式需求/设计和实现任务；若决定不做，记录依据后设为 `已取消`；若证据仍不足，保留结论与下一步验证责任，不得标记为已完成的产品实现。完成或取消的包均保留 proposal、规格/设计（如有）、任务状态和证据摘要，供后续会话追溯；未交付的行为不能合入当前基线。

## 6. 原型先行的回填规则

允许在规格完整前做只为回答关键问题的短小验证，例如 RK3588 编码/推理性能、WebRTC/HLS 兼容、MQTT 断网重传、模型在新场景上的效果。原型开始前应明确要回答的问题、停止条件、影响面和是否可丢弃；不得以原型代码默认成为正式产品架构。取得结果后，将可观察证据记录在 Research 或 proposal，并修订需求/设计中的假设。结论为继续时，补齐正式验收条件和实现任务；结论为停止时记录理由并取消归档；结论不确定时明确下一轮验证和负责人，保持 `探索中`，不能宣称已完成。若原型直接演进为正式代码，同样补齐其变更包并执行相应检查。

## 7. 结束时的交付说明

报告变更包位置/状态、实现范围、按验收点/AC 逐项提供的证据、未验证项、回写的基线文件和已知风险。证据可以是自动化检查、接口结果、UI/设备实测、日志或可复现步骤。硬件/模型结果说明真实设备、固件/模型/数据版本和测试限制；模拟结果不能宣称为实机验收。只有所有适用任务完成、验收证据有记录、基线同步且未解决项已明确时，才能标记 `已完成`。PR 合并、部署或用户验收仍按仓库原有流程处理，不以归档状态代替。
