# 行为规格：三类用户与工作空间授权

> 关联提案：[proposal.md](proposal.md)<br>
> 状态：目标合同草案；本文件的需求尚未由实现或旧验收记录证明。<br>
> 来源：[PRD](../../Analysis/PRD.md)、[全局 SPEC](../../Analysis/SPEC.md)、[系统结构](../../Design/STRUCTURE.md)及 2026-10-29 的现状评审。

## 范围和术语

- **账号类型**：服务端保存的 `admin`、`pc` 或 `mobile`。设备类型、屏幕尺寸和客户端参数不决定角色。
- **工作空间**：PC 账号拥有的资源租户。首版每个 PC 账号一个，只有一个 owner；owner 对其全部业务资源有管理权限。
- **移动成员**：通过邀请加入一个工作空间的 `mobile` 账号。账号全局最多有一个有效成员关系。
- **设备授权**：成员对某工作空间中指定设备的一组能力。事件、截图、告警和实时视频沿用该设备范围。
- **平台管理员**：可管理平台账号、查看系统健康与审计元数据；默认没有任何工作空间成员关系。
- **租户资源**：设备、摄像头、算法配置、媒体来源、事件及其统计等归属工作空间的数据。
- **用户主体记录**：登录会话、处置操作人、媒体观看者、Push 订阅/接收人等记录；其中 `account_id` 保持表示实际用户，不自动改成 `workspace_id`。

需求覆盖三类入口与 auth、device、event、media、push、Web/PWA 和部署迁移；不改变 Atlas Agent/MQTT 设备协议。`/admin`、`/app`、`/m` 是拟议路由，具体兼容路径由 Web 规格组确认。

## 需求与验收条件

### REQ-01：服务端身份类型与账号生命周期

auth-service 应为每个账号保存服务端生成的类型和状态。浏览器提交的字段、请求头、URL 或修改本地状态不能更改身份。`GET /api/v1/auth/me`（或等价接口）返回当前服务端确认的类型。

**验收条件**

- **AC-01.1** 注册请求不含可写的 `user_type`；自助注册只能创建 `pc`。移动账号只能通过有效邀请兑换创建或激活，管理员账号只能通过受控初始化或已认证管理流程创建。
- **AC-01.2** `me`、登录和内部会话校验返回/使用同一个服务端身份。伪造 `X-Account-ID`、`X-Session-ID`、`X-User-Type` 或工作空间头不能扩大权限。
- **AC-01.3** 停用账号后，后续会话验证和业务授权失败；停用操作撤销或使该账号的现有会话失效，并产生审计记录。
- **AC-01.4** PC 自助注册与管理员受控创建并存，服务端创建的账号类型固定为 `pc`；移动账号只能经邀请绑定。停用 PC owner 后，其工作空间进入受限状态，成员访问一并拒绝，本期不转移所有权。管理员不能修改部署配置或重启服务。

**验证方式**：auth-service 隔离 PostgreSQL/API 集成测试；Nginx 身份头伪造测试；账号状态与会话撤销验证。

### REQ-02：工作空间和资源归属

PC 账号拥有唯一工作空间。租户资源必须按工作空间读取和写入；授权判断不能仅依赖当前登录账号与资源 ID 是否存在。

**验收条件**

- **AC-02.1** 每个 PC 账号最多一个工作空间，每个工作空间恰有一个 owner；PC 可修改允许的展示信息，但不能通过 API 设置工作空间 ID、owner 或资源的工作空间。
- **AC-02.2** 每个租户资源在创建时获得可信工作空间归属；设备/摄像头、媒体来源、事件和统计查询的范围一致。
- **AC-02.3** 由工作空间 A 的 PC 用户或成员读取、修改工作空间 B 的资源时，服务端拒绝请求且不泄露资源存在性；用 A/B 两组数据覆盖列表、详情、写入、证据、播放和统计。
- **AC-02.4** PC owner 停用导致工作空间受限时，owner 和成员的业务访问按提案确认的策略统一执行；不发生未审计的所有权转移。

**验证方式**：各服务跨租户集成测试、数据迁移计数与孤儿核对。

### REQ-03：邀请、成员关系和设备级权限

PC owner 可为自己的工作空间创建一次性邀请，并给定可访问设备及其能力。移动用户不能修改成员关系、工作空间或自身权限。

**验收条件**

- **AC-03.1** 邀请与工作空间、创建者、有效期、使用/撤销状态关联；数据库只保存随机 token 的哈希。过期、撤销或已使用邀请不能兑换，兑换与消耗在同一事务内完成。
- **AC-03.2** 移动账号最多加入一个工作空间；重复邀请/绑定、将 PC 或管理员账号转换为 mobile，以及从客户端提交另一工作空间 ID 均被拒绝。
- **AC-03.3** 权限按设备授予，能力至少包含 `device.read`、`event.read`、`event.handle`、`stream.view` 和 `alert.receive`；一个设备的能力不能隐式扩大到其他设备或能力。
- **AC-03.4** owner 可查看成员和邀请、变更成员设备授权、撤销邀请或成员。撤销一旦提交，后续授权判定立即失败；相关会话、租约和 Push 收件人进入撤销/重算流程。
- **AC-03.5** 邀请创建/兑换/撤销及授权变更能按 actor、workspace、member/invitation、结果、request ID 和时间审计；不得记录原 token、密码、RTSP URL 或会话秘密。
- **AC-03.6** 移动成员可以查看自己的工作空间名称、成员状态和逐设备权限；不能修改、添加或扩大这些授权。

**验证方式**：邀请过期/重复/并发兑换测试、成员授权矩阵测试、服务端审计记录核对。

### REQ-04：服务端角色与资源授权

所有服务端业务入口在执行读写前验证会话、账号类型、工作空间、资源归属和操作能力。前端路由和隐藏菜单只是导航控制，不构成安全边界。

**验收条件**

- **AC-04.1** PC owner 可以对自己工作空间内资源执行本规格定义的管理操作；不能访问其他工作空间。
- **AC-04.2** mobile 只能对有效成员关系及被授权设备执行相应操作；缺少 `event.handle` 时不能处置，缺少 `stream.view` 时不能播放，缺少 `event.read` 时不能查看事件和截图。
- **AC-04.3** admin 仅能访问显式管理员 API；管理员身份不会自动映射为任意 workspace/device/event/stream 权限。
- **AC-04.4** 未登录返回未认证；账号/成员/工作空间已停用或权限不足返回一致的拒绝响应。跨工作空间资源使用 404 或等价不泄露语义；依赖授权服务不可用时 fail closed。
- **AC-04.5** 所有客户端身份转发头先由 Nginx 清除，再从 auth-service 验证结果生成；业务服务只接受来自受信任本机代理或服务身份的上下文。

**验证方式**：跨角色 API 矩阵测试、身份头伪造测试、授权服务故障注入。

### REQ-05：共用媒体授权和撤权

三类用户共用现有 media-service 与 MediaMTX。来源配置和媒体密钥仍由 media-service 管理；mobile 只能对有 `stream.view` 权限的摄像头取得单路播放租约。

**验收条件**

- **AC-05.1** PC 只能配置/播放自己工作空间中的摄像头；mobile 播放前及受保护的 WebRTC 信令、HLS 播放列表/分片请求均校验当前成员权限和租约。
- **AC-05.2** RTSP 源地址、凭据、MediaMTX 控制接口不会返回给浏览器、Push 通知或管理员健康页；播放 URL/ID 不能单独构成访问授权。
- **AC-05.3** 成员、账号、设备或会话撤销后，租约续期和后续媒体授权被拒绝；MediaMTX 中已建立的观看连接按提案确认的时限终止，并在失败时保留待处理状态、重试和告警。
- **AC-05.4** 原有 WebRTC 优先、HTTPS HLS 回退、来源对账和容量限制继续工作；最多 12 路活动源与 24 个观看连接仍是实测目标，不因移动单路入口增加额外预算。

**验证方式**：media-service 隔离集成测试、受保护媒体请求测试、MediaMTX/浏览器/目标网络容量实测。

### REQ-06：事件、证据、处置和 Push 范围

事件和证据按 workspace 归属；移动成员的数据范围跟随设备授权。通知接收人由事件所属 workspace、设备授权和当前成员状态共同决定。

**验收条件**

- **AC-06.1** PC owner 可查看工作空间内事件；mobile 仅能读有 `event.read` 的设备事件、有效截图，并仅在有 `event.handle` 时执行合法状态流转。处置历史继续记录执行账号。
- **AC-06.2** 截图成功上传后可查看 24 小时；过期后、授权撤销后或跨工作空间时不得经历史 URL 访问；事件和处置历史按既有保留合同继续存在。
- **AC-06.3** Push 仅投递给当前有效且获该设备 `alert.receive` 权限的移动成员订阅；投递重试时重新计算有效接收人。通知只含必要摘要与详情链接，不含截图、RTSP、会话或凭据。移动成员只能管理自己的订阅；PC owner 可按成员和设备撤销告警接收权限。
- **AC-06.4** 通知点击后重新验证登录、成员关系和事件权限；已撤权、事件已处理或证据过期时展示当前状态，不沿用历史通知中的授权。
- **AC-06.5** 工作空间统计只统计当前用户可访问的设备范围；不混合其他 workspace 数据，移动摘要不暴露未获授权设备的计数。

**验证方式**：event-service 与 push-service 隔离集成测试、证据 URL 撤权测试、PWA Push 点击和账号切换验收。

### REQ-07：管理员入口、平台健康与审计

管理员由受控方式初始化；不提供公开管理员注册。管理页提供账号/平台运行元数据和审计查询，不呈现客户业务内容。

**验收条件**

- **AC-07.1** 无管理员身份的 PC/mobile 访问 `/admin` 和 admin API 均被服务端拒绝；管理员只能创建/停用/恢复明确允许的账号类型和查看已定义的系统健康数据。
- **AC-07.2** admin 不能直接读取 RTSP URL、客户实时视频、事件截图或其他 workspace 业务明细；限时协助查看视频属于后续独立需求。
- **AC-07.3** 管理员初始化、账号状态变更、审计查询和其他高风险操作记录 actor、目标、原因（适用时）、结果、request ID 与时间；日志不可由普通客户改写。
- **AC-07.4** 健康信息来自五个现有服务及 PostgreSQL/MQTT/MediaMTX 的可用性检查；不把本机任意 shell、配置文件或完整服务日志暴露为 Web 功能。

**验证方式**：管理 API 权限测试、审计字段/脱敏核对、部署环境 health 探针验证。

### REQ-08：角色化 Web/PWA 导航

同一 Vue 3 应用可按角色呈现管理员、PC 工作台和移动 PWA 导航；角色由 `/auth/me` 等服务端身份决定。每种身份在本产品范围内的日常业务操作都必须可从对应界面完成，普通用户无需手工调用 API、SQL 或命令行。首次创建平台管理员和主机级部署/运维属于受控基础设施操作，不在 Web 控制台范围内。

**验收条件**

- **AC-08.1** 管理员进入管理路由，PC 用户进入工作台路由，mobile 进入 `/m` 路由；直接访问他人角色路由时安全跳回本人入口或显示拒绝页。
- **AC-08.2** mobile 界面不提供设备激活、RTSP 来源编辑、算法/规则管理、成员管理或 12 分屏监控；仅提供授权设备、事件、通知、单路视频和账号设置。
- **AC-08.3** PWA 静态缓存策略继续只缓存应用壳与静态文件；API、截图和媒体内容不进入 Service Worker 缓存。旧 PC 路由和既有 Push 深链的迁移映射由前端规格确定。
- **AC-08.4** 登出、账号切换、角色停用或授权变更后，前端清除旧账号 CSRF/页面状态并重新验证目标资源。
- **AC-08.5** PC 工作台页面可完成账号/工作空间基本资料、设备登记/编辑/停用、Atlas 引导接入/激活/续期、摄像头 RTSP 来源配置与状态查看、规则配置、监控、事件处置和统计，不要求用户自行调用 API 或数据库。首次 SSH 引导必须在页面展示待确认设备指纹、接入状态/失败结果；用户提交后密码清空，错误状态可在页面重试，不要求手工执行 API 或进入开发板命令行。复用现有私网 CIDR allowlist、host-key pinning 和异步 provisioning job 安全合同。
- **AC-08.6** PC 成员页面可创建/撤销邀请、查看成员、按设备分别授予或撤销 `device.read`、`event.read`、`event.handle`、`stream.view`、`alert.receive`，并显示每个设备的摄像头范围；首版 `stream.view` 对所选设备下所有摄像头生效。
- **AC-08.7** 移动 PWA 页面可完成邀请兑换/登录、查看自己的工作空间与设备授权、管理自己的 Push 订阅、查看授权设备/事件/有效截图、处理事件，并在获 `stream.view` 时打开单路摄像头；同一 PWA 会话最多存在一条活动播放租约，切换摄像头或离开页面时先释放上一租约。没有权限、邀请过期或证据过期时显示明确状态。Push 首次订阅通过用户手势发起浏览器权限请求，并呈现拒绝、不可用和已订阅状态；不能绕过浏览器/操作系统的通知授权设置。
- **AC-08.8** 管理员控制台可完成日常 PC 账号创建/停用/恢复、受控移动账号停用/恢复、平台健康查看、脱敏诊断和审计查询。首个 admin 初始化与主机级部署配置/服务重启由受控运维流程完成，不提供通用 shell 或任意配置编辑界面。

**验证方式**：路由/组件测试、桌面与真实手机 PWA 验收、Push 深链回归。

### REQ-09：分阶段迁移和回滚

所有当前 PC 账号的租户资源迁移到唯一工作空间；迁移保留资源和业务历史，在验证完成前保持可回滚。

**验收条件**

- **AC-09.1** 每个有效旧 PC 账号恰有一个 workspace；原设备、摄像头、媒体来源、事件、处置、统计与通知关系可追溯到同一 workspace。无法匹配账号的记录进入人工核对清单，不静默归属。
- **AC-09.2** 会话、处置 actor、观看者、Push 订阅及接收者等用户主体字段保持用户语义；只对真正由账号拥有的租户资源增加/回填 `workspace_id`。
- **AC-09.3** 每个服务先扩展字段并兼容旧读写，再回填、校验双读结果、切换授权；迁移前备份并在隔离副本完成回滚演练。
- **AC-09.4** 数据计数、唯一性、孤儿关系和 A/B 双租户隔离全部通过后才允许切换；兼容列在回滚窗口结束前不得清理。
- **AC-09.5** Atlas 事件仍由可信设备绑定关系推导租户，不信任边缘上报 `account_id`；MQTT/激活凭据不因租户迁移而轮换或泄露。

**验证方式**：副本数据库迁移、回滚、旧账号登录和双租户隔离；设备协议回归。

### REQ-10：代码边界与分层依赖

实现三类用户目标时，代码应沿服务所有权逐步形成可检查的分层，保持现有服务、Web 工程和 Atlas runtime 的职责边界。分层为渐进重构目标，不要求全量重写。

**验收条件**

- **AC-10.1** 每个 Go 服务的 cmd 目录只作为组合根；入站 HTTP/MQTT/worker 适配器调用 application 用例，服务内业务规则不留在 Gin handler 或 main 中。
- **AC-10.2** application 层承载用例并定义所需出站端口；domain 层包含实体、值对象、策略和状态机，不依赖 Gin、GORM、MQTT、MediaMTX 或部署 SDK。
- **AC-10.3** PostgreSQL、服务 HTTP、MQTT、MediaMTX、Push 和文件卷适配器通过端口连接用例；数据库写入仍只由所属服务负责。
- **AC-10.4** 服务间不导入其他服务的 Go package、不共享可变领域对象、不跨 schema 联表；集成仅通过有版本的 HTTP、MQTT 或 outbox 合同。
- **AC-10.5** Web 保持 presentation、feature/use-case/state 与 typed API adapters 的职责边界；组件不直接绕过 API client，前端路由/隐藏按钮不能代替服务端授权。
- **AC-10.6** Atlas 的组合入口、runtime 用例、硬件/协议适配器与算法插件接口可独立辨认；平台硬件细节不渗入业务策略，插件经稳定接口接入。
- **AC-10.7** 自动依赖检查能发现 domain 框架导入、服务间包依赖及循环依赖；违规会阻断合并，例外必须有明确边界和有效期限。
- **AC-10.8** 重构按服务和垂直切片推进；每个切片保留既有外部合同与资源所有权，并提供对照验收证据；不得以目录搬迁或全量替换掩盖行为变化。

**验证方式**：模块依赖图/静态检查、服务级用例与适配器验证、API/MQTT/媒体合同回归、Web 页面与 Atlas 目标设备的分阶段证据。

## 不变项与兼容要求

- 保留现有五个 Go 服务、Vue 3/TypeScript、PostgreSQL、MQTT、MediaMTX、Nginx 和原生部署边界。
- 保留 Atlas 200I DK A2、设备 Agent、现有激活、MQTT、AI 模型和规则 ACK 链路。
- 保留 RTSP 输入、media-service 来源密钥与 MediaMTX 对账、观看租约、WebRTC/HLS、12 路活动源/24 个观看连接的目标边界。
- 保留当前 24 小时截图期限、event_id 幂等、处置版本并发控制、Push outbox 与不缓存敏感 API 的规则。
- 保留当前账号唯一用户名策略，除非注册/身份评审另有明确决定；账号类型不可由用户名格式推断。
- 旧资源 ID、设备 MQTT 身份、事件 ID 和历史处置记录不因增加 workspace 而重建。

## 数据处理和保留

- auth-service 新增账号类型/状态、workspace、workspace member、邀请、设备能力授权和审计记录；邀请原 token 只在创建/兑换时出现。
- device、media stream、event 等租户资源增加 `workspace_id`。迁移期间 `account_id` 与 `workspace_id` 双写/双读并校验；首版建议 `workspace_id = owner_account_id`，使原归属可直接回填。
- media viewer lease 的 `account_id` / `session_id` 继续标识观看者；event disposition 的 `actor_account_id` 继续标识处置人；Push subscription/delivery 的账号字段继续标识订阅主体/接收人。
- 所有审计记录不包含密码、Cookie/session token、原始邀请 token、RTSP URL、截图数据、MQTT 凭据或 Push endpoint 私钥材料。
- 24 小时截图期限和既有事件留存策略不随工作空间迁移改变。

## 明确不做

- 管理员默认查看客户 RTSP、直播、截图或全量事件详情。
- 账号跨多个工作空间、移动成员同时加入多个工作空间、成员转移到其他空间、无审计的 owner 转让。
- 新建独立媒体服务或为不同角色复制业务数据与业务 API。
- 手机多路监控墙、原生移动 App、ONVIF 自动发现、对象存储迁移和通用审批工作流。
- 使用客户端 `user_type`、`workspace_id`、角色路由或静态播放地址作为授权依据。
