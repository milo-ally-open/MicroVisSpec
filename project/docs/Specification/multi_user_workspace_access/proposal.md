# 提案：三类用户与工作空间授权

> 状态：待评审（代码现状评审与产品默认规则已确认，实现和跨服务合同同步待推进）<br>
> 路径：跨边界/高风险<br>
> 负责人：产品与平台负责人<br>
> 上游合同：[PRD](../../Analysis/PRD.md)、[全局 SPEC](../../Analysis/SPEC.md)、[系统结构](../../Design/STRUCTURE.md)

## 背景与评审结论

当前产品合同和实现均采用单账号租户：用户自助注册；设备、事件、媒体来源与 Push 订阅按账号隔离。该模型已支撑 MVP 的设备接入、事件处置、媒体播放和 PWA 通知，但不能表达平台管理员、客户空间成员或成员级设备授权。

评审建议保留方案中已有的设备与媒体链路，重做身份和授权边界，并补齐移动成员权限与撤权语义。方案不应把当前代码描述成已有三类用户，也不应将所有 `account_id` 统统替换成 `workspace_id`：仓库中有些 `account_id` 是资源租户，有些代表会话用户、视频观看者或 Push 接收人，语义不同。

建议的首版目标：

- 管理员账号与客户工作空间分离，只能执行平台账号管理、健康查看和审计查询；默认没有客户 RTSP 地址、直播流或事件截图权限。
- PC 用户每人拥有一个工作空间，对其中资源有完整管理权。为兼容现有注册行为，保留 PC 自助注册，同时允许管理员受控创建、停用和恢复 PC 账号。
- 移动用户仅通过工作空间邀请加入；每个移动账号最多绑定一个工作空间。成员权限按设备分别授予 `device.read`、`event.read`、`event.handle`、`stream.view`、`alert.receive`，不能由客户端自行扩大。
- 每类用户在产品范围内的日常操作均应有对应 Web/PWA 页面，不要求通过手工 API、SQL 或命令行完成：PC 页面覆盖设备登记/激活/续期、RTSP 配置、规则、监控、事件、成员邀请和权限；移动页面覆盖邀请绑定、授权范围查看、通知、事件处置和授权视频；管理员页面覆盖日常账号管理、健康和审计。
- 成员撤销后，新的 API、截图和媒体授权请求立即失败；已建立的直播连接在服务健康时 30 秒内断开，故障时保留撤销状态并重试。
- 管理端首版只提供健康、脱敏诊断和审计页面；部署配置修改与服务重启继续由主机受控运维流程执行，不开放通用 shell/配置编辑 API。
- `stream.view` 按设备授予，并覆盖该设备下的所有已登记摄像头；界面应显示摄像头清单。移动成员设备数不设静态硬上限，实际受平台资源和容量验收约束。
- 现有 Atlas、RTSP、MediaMTX、Agent/MQTT、模型规则、24 小时截图和浏览器 WebRTC/HLS 链路继续作为底层基线。

**界面范围解释**：本文的“用户可直接在界面完成操作”指三类身份在各自业务范围内无需手工 API、SQL 或命令行完成日常操作，不包括受控部署行为（首个 admin 初始化、主机配置和服务重启）。设备的首次 SSH 引导是 PC 工作台的业务向导：用户确认设备指纹、输入现场管理员提供的临时凭据并查看任务结果；平台不得持久化或记录密码。它与成员对设备能力的授权是两种不同流程。

## 现状依据与约束

| 领域 | 仓库现状证据 | 评审结论 |
|---|---|---|
| 身份 | `auth-service` 的 `Account` 只有 ID、用户名和密码哈希；公开注册、登录、会话校验按账号工作，未见 `user_type`、账号状态或管理员引导接口。 | 新身份类型必须由服务端创建；普通注册参数不能写角色。 |
| Web/PWA | `src/router/index.ts` 有 `/login`、`/register` 和统一 `/` 工作台子路由；`DeviceDetailPage.vue` 已提供 SSH host-key 指纹确认、首次接入任务轮询、激活/续期及摄像头/RTSP 管理；`MonitorPage.vue` 与 `CameraPlayer` 支持最多 12 路并在窄屏呈现单路布局。 | 当前页面仍是同一账号的个人工作台；无 admin/mobile 角色路由、邀请/成员授权与按能力过滤。目标应复用设备接入和播放器，并补齐角色入口与移动成员授权语义，不重做已有流程。 |
| 设备与事件 | device、event 行以 `account_id` 过滤；事件处置另存 `actor_account_id`。已有双账号隔离集成用例。 | 资源租户增加工作空间范围；处置人仍是执行操作的账号。 |
| 媒体 | media-service 加密保存来源；流记录按 `account_id` 所有；观看租约同时记录观看者账号、会话和流；已有 Nginx/media-service 授权与撤租机制。 | 区分“资源所属工作空间”和“观看者账号”；复用单一媒体控制面。 |
| Push | 订阅绑定 `account_id` 与 `source_session_id`，事件投递按账号选择订阅；已有 session.revoked 消费。 | 订阅继续属于账号；接收人改由工作空间、设备授权和移动成员状态求得。 |
| 部署与数据库 | 五个 Go 服务分别使用独立 PostgreSQL schema/角色并自行迁移；前端由 Nginx 托管。 | 服务不能依赖跨 schema 直接联表；统一成员授权应提供受认证的内部合同。 |
| 源码层次 | Go 实现主要集中于各服务 cmd/service-name 的 main package；Web 有 api/state/pages 等目录和已落地的设备/监控页面；Atlas 有 common/agent/manager/media/plugins。 | 当前是按服务/子系统组织，尚无统一、可验证的 application/domain/adapters 依赖规则；须增量拆分，不做全量重写。 |
| 当前验证边界 | 任务与 evidence 记录了本机/集成测试、双账号隔离、部分 MQTT/Atlas 联调；真实手机 Push、媒体容量和完整实机闭环仍有待验收。 | 新方案的 AC 不能由旧基线证据代替。 |

主要代码依据：`project/src/services/auth-service/go/cmd/auth-service/main.go`、`device-service/go/cmd/device-service/main.go`、`media-service/go/cmd/media-service/models.go`、`event-service/go/cmd/event-service/models.go`、`push-service/go/cmd/push-service/models.go`、`project/src/clients/web/src/router/index.ts`、`pages/DeviceDetailPage.vue`、`pages/MonitorPage.vue`、`components/CameraPlayer.vue`。详见各领域的 `tasks.md` 与 evidence 文件。

### 界面覆盖评审结论

现有实现已经让当前账号用户从 Web 界面完成设备登记、首次 SSH 引导接入、指纹确认、接入进度查看、设备激活/续期、摄像头登记与 RTSP 配置，以及最多 12 路的桌面监控；窄屏播放器呈现单路画面。设备 SSH 凭据由用户在当前向导临时输入，服务端执行受限引导任务，前端完成后清空密码字段。该能力应列为既有流程回归项。

但当前路由和服务端仍按一个 `account_id` 工作。仓库尚无三类角色、工作空间成员、邀请兑换、逐设备能力 grant、mobile 授权范围页或管理员控制台。因此“已有用户可通过界面接设备和看视频”成立；“不同角色已各自能在界面完成所有操作”不成立。目标方案补齐的是 admin/PC/mobile 的差异化闭环，尤其是 owner 在页面授权/撤权、移动成员查看本人授权设备并只播放获批设备的单路视频。授权判定必须落在服务端；前端只展示范围和状态。

## 目标与成功观察

- 服务端可以明确区分 `admin`、`pc`、`mobile`，并在所有用户可触达的 API 上实施角色与资源范围校验。
- PC 工作空间拥有设备、来源、事件及规则；获授权移动成员可按设备查看状态、事件、截图、视频或执行处置。
- 管理员可管理账号、查看平台健康和审计，但不能仅凭管理员身份读取客户内容。
- 撤销成员、停用账号或停用设备后，后续访问被拒绝，媒体租约和通知接收关系完成收敛。
- 迁移后原 PC 账号继续访问原设备、事件和处置历史；跨账号负向用例通过。

## 范围

### 本次包含

- 服务端角色、账号状态、工作空间、移动成员、邀请和设备级权限。
- auth-service 的角色认证、会话撤销、邀请/成员管理、管理接口和可审计操作。
- device、event、media、push 的工作空间资源范围与移动成员授权。
- 管理员、PC 工作台和移动 PWA 的角色入口与路由守卫。
- 分阶段 schema 扩展、旧资源回填、回滚和跨角色隔离验证。

### 本次不包含 / 保持不变

- Atlas 200I DK A2、Agent/MQTT 激活、课堂模型和规则配置协议不因用户角色而改变。
- 摄像头仍以 RTSP 接入；media-service 继续管理来源密钥、MediaMTX 对账、观看租约与配额。
- WebRTC 优先、HTTPS HLS 回退；截图上传后可查看期限仍为 24 小时。
- 不新增原生 App、ONVIF 自动发现、跨工作空间访问或通用工作流引擎。
- 首版管理员只看平台运行元数据；客户视频临时协助访问不纳入本次实现。

## 备选方案与建议

| 方案 | 收益 | 成本/风险 |
|---|---|---|
| 继续把每个账号当作唯一租户 | 改动最少 | 无法实现移动成员共享和角色差异。 |
| 新增工作空间与集中成员授权，复用现有五个服务 | 维持服务边界，权限有单一管理点，设备/事件/媒体服务仍拥有本域数据 | 增加 auth-service 在线授权依赖；需要多 schema 迁移和撤权补偿。 |
| 为管理员、PC、手机分别复制业务服务或数据 | 表面上入口清楚 | 数据复制、授权漂移和媒体实现重复，违背共用后端目标。 |

建议采用第二种。工作空间授权由 auth-service 管理，业务服务仍负责本地资源归属及操作；新内部授权调用失败时按拒绝处理。工作空间 ID 建议在首版沿用其 PC 所有者账号 UUID，旧资源可直接回填，避免一次跨 schema ID 映射；若未来允许所有者迁移，再单独定义稳定 workspace ID 的转换。

## 影响面、依赖与风险

- 受影响基线：PRD、全局 SPEC、STRUCTURE、auth/device/media/event/push/web_pwa_client/platform_deployment 规格组。
- 数据：设备、摄像头、算法配置、媒体流、事件和统计等租户资源增加 `workspace_id`；旧 `account_id` 暂留用于兼容和核对。会话、事件处置人、媒体观看者、Push 订阅和投递接收人的账号字段继续表示用户，不做机械替换。
- API：新增邀请/成员/平台管理/内部授权合同；现有用户业务 API 逐步按工作空间授权。
- 兼容：Nginx auth 子请求继续清理客户端身份头；新角色和工作空间上下文只能由 auth-service 验证后写入。Atlas 事件仍由 device-service 从设备绑定关系推导租户，不信任设备上报的租户 ID。
- 风险：auth-service 作为授权决策依赖会增加服务间延迟与故障耦合；撤权事件、MediaMTX 断流、Push 收件人重算和迁移回滚必须覆盖。
- 回滚：先加列和双写，再回填、切换读取；保留旧列与备份，完成跨账号核对前不删除兼容字段。
