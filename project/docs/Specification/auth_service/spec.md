# auth-service 实现任务书

> 状态：首发实现任务书；以[产品需求](../../Analysis/PRD.md)、[架构设计](../../Design/STRUCTURE.md)和[总技术规格](../../Analysis/SPEC.md)为准。
>
> 责任边界：auth-service 只负责账号、密码、会话与会话撤销；各业务服务按可信 account_id 对自己的资源再次授权。
>
> 首发边界：仅支持用户名和密码注册、登录、查看本人信息、退出及使用旧密码改密；不实现成员邀请、共享、组织、角色或找回密码。

## 稳定需求与验收索引

> 本索引用于跨文档追踪；详细行为以本文件正文为准。编号保持稳定，需求变更时同步更新。

### REQ-01 账号与会话安全

账号、会话和机密须按最小暴露原则持久化管理。

- **AC-01.1**：敏感材料不进入仓库、镜像或日志，必需依赖健康状态准确。
- **AC-01.2**：账号/会话数据仅由本服务管理。

### REQ-02 浏览器身份生命周期

浏览器支持首发范围内的账号和会话操作。

- **AC-02.1**：注册、登录、本人信息返回一致身份。
- **AC-02.2**：退出和改密按规格撤销会话，错误遵守统一合同。

### REQ-03 身份与资源隔离

可信身份上下文贯穿服务间授权。

- **AC-03.1**：未验证身份或伪造身份头按规格拒绝。
- **AC-03.2**：业务服务按可信 account_id 检查资源归属。

### REQ-04 撤销传播

会话撤销可靠传播到订阅方。

- **AC-04.1**：撤销记录与 outbox 原子提交且可幂等消费。
- **AC-04.2**：下游最终清理相关订阅或租约且可观测。

## 一、任务目标

交付可独立运行的 Go/Gin/GORM 服务，使账号成为设备、事件、媒体和推送数据的统一归属单位。浏览器通过 Nginx 和同源 Cookie 使用会话，其他服务只接收经过验证的身份上下文。

阶段顺序：服务基础 → 注册与登录 → 会话鉴权 → 退出与改密 → 跨服务联调和交付。每一阶段须完成对应交付物与验收后再进入下一阶段。

---

## 二、第一阶段：服务基础与数据所有权

### 2.1 实现任务

1. 在 `project/src/services/auth-service` 内建立 Go 模块、Gin 入口和配置加载；发布时构建为独立 Go 二进制，由 systemd 管理。服务提供内部 `/health/live` 与 `/health/ready`；就绪状态反映必需的 PostgreSQL 依赖。
2. 在 PostgreSQL `auth` schema 中建立 `accounts`、`sessions` 和 `outbox`，由本服务独占迁移和数据库账号。账号 ID、会话 ID 与 outbox 事件 ID 为 UUID；用户名规范化值、会话 token 哈希分别建唯一索引。时间存为 `timestamptz`。
3. 明确配置与机密注入：数据库凭据、会话 Cookie 配置、内部服务凭据和加密/签名材料来自部署环境，不写入仓库、镜像或日志。
4. 对外 API 使用 `/api/v1`，内部会话校验与服务间事件入口使用 `/internal/v1`；错误响应遵守总 SPEC 的 `error.code`、`error.message`、`request_id` 合同。

### 2.2 交付物与阶段验收

- 交付可启动二进制、迁移、配置示例和健康接口说明。
- 重启服务后账号与会话记录仍由 PostgreSQL 保存；服务不可连接数据库时 `/health/ready` 不报告成功。
- 使用受限数据库账号无法读写其他服务 schema；空库可按确定顺序迁移。

## 三、第二阶段：注册、登录与本人信息

### 3.1 浏览器 API

| 方法与路径 | 任务与返回 |
| --- | --- |
| `POST /api/v1/auth/register` | 接收 `username`、`password`；返回 `account_id`、`username`，注册后不自动登录。 |
| `POST /api/v1/auth/login` | 验证用户名和密码；返回账号基本资料及 `csrf_token`，设置会话 Cookie。 |
| `GET /api/v1/auth/me` | 根据有效会话返回 `account_id`、`username`、`csrf_token`；无效会话返回 401。 |

### 3.2 实现任务

1. 用户名规范化后执行唯一约束；仅接受 3–32 位 ASCII 字母、数字与下划线。密码不少于 12 个字符；重复用户名和输入错误返回稳定业务错误。
2. 用 Argon2id 保存密码哈希，并为参数版本保留迁移能力。登录时使用安全的密码验证；失败响应不暴露用户名是否存在。
3. 登录成功创建不可猜测的 opaque token，数据库仅保存其哈希。Cookie 设置 `Secure`、`HttpOnly`、`SameSite=Lax`、`Path=/`；会话闲置 7 天过期，服务端校验撤销、到期和最后活动时间。
4. 注册与登录设置限流，并记录登录成功/失败审计；日志不记录密码、Cookie、原始 token 或 CSRF token。
5. `GET /me` 支持刷新页面后恢复登录态和 CSRF token；不将会话 token 放入 JSON 或浏览器持久化存储。

### 3.3 交付物与阶段验收

- 提交三条 API 的请求/响应定义及账号和会话迁移。
- 可独立注册两个账号并分别登录；重复用户名、弱密码、错误密码、过期或伪造 Cookie 均得到规定响应。
- 数据库和日志中看不到明文密码与原始会话 token；页面重载后 `GET /me` 能恢复有效会话。

## 四、第三阶段：Nginx 鉴权和账号隔离

### 4.1 实现任务

1. 提供内部会话校验接口，仅接受 Nginx 的 `AUTH_INTERNAL_SERVICE_TOKEN` 或 media-service 的专用 `AUTH_MEDIA_SERVICE_TOKEN`；有效会话返回可信 `account_id`、`session_id`，无效会话返回 401。接口路径和头字段在 OpenAPI/部署配置中固定，内部端口不对公网开放。
2. Nginx 对受保护的 `/api/v1` 请求发起 `auth_request`，先清除客户端传入的 `X-Account-ID`、`X-Session-ID` 等身份头，再写入校验后的值。Gin 只信任本机 Nginx 反向代理。
3. 所有带 Cookie 的写请求校验 `Origin`，并要求与当前会话关联的 `X-CSRF-Token`；注册/登录等尚无会话的入口按同源 `Origin` 检查与限流处理。前端请求客户端在登录后或重载后获取 token 并附于写请求。
4. 内部调用使用按服务区分的可轮换凭据；业务服务仍须在资源查询中加 `account_id` 条件，不因有可信身份头就放过跨账号资源 ID。

### 4.2 交付物与阶段验收

- 交付 Nginx 授权子请求配置、内部接口合同、前端会话恢复接线说明。
- 未登录访问受保护 API 返回 401；伪造身份头、跨站写请求或缺失/错误 CSRF token 无法修改资源。
- 账号 A 带账号 B 的资源 ID 调用设备、事件、截图、媒体和订阅接口，均不能读取或修改 B 的数据。

## 五、第四阶段：退出、旧密码改密与会话撤销

### 5.1 浏览器 API

| 方法与路径 | 任务与返回 |
| --- | --- |
| `POST /api/v1/auth/logout` | 撤销当前会话、清理 Cookie；重复退出按成功处理。 |
| `PUT /api/v1/auth/password` | 接收 `old_password`、`new_password`、`new_password_confirmation`；成功后撤销账号全部旧会话并要求重新登录。 |

### 5.2 实现任务

1. 改密校验旧密码、新密码长度与两次输入一致性；失败时密码与现有会话不变。成功时重新生成 Argon2id 哈希并撤销该账号全部旧会话。
2. 退出只撤销当前会话；改密对该账号每个旧会话各生成一条撤销消息。撤销会话时，在同一数据库事务中写入含稳定事件 ID、`account_id` 和 `session_id` 的 `session.revoked` outbox；由异步投递器通知 push-service 与 media-service，失败可重试并幂等消费。
3. 退出路由由 auth-service 自行校验有效会话、同源 `Origin` 与 CSRF，不让通用 Nginx `auth_request` 在重复请求时抢先返回 401。对已经撤销的会话，仅同源重复退出清 Cookie 并返回成功，不再改变状态。
4. push-service 收到撤销事件后停用由该会话创建的订阅；media-service 终止该会话的观看租约与现存播放。会话普通自然过期只影响页面与详情访问，不自动取消用户同意的后台 Push 订阅。
5. Cookie 清理使用与设置一致的作用域属性；多次点击退出和 outbox 重投不产生额外副作用。撤销到投递的短暂延迟需通过队列积压指标观察。

### 5.3 交付物与阶段验收

- 交付改密/退出 API、`session.revoked` 消息合同、outbox 投递器和会话撤销审计。
- 错误旧密码、确认值不一致均被拒绝；改密后所有旧会话访问受保护 API 返回 401，退出只影响当前会话。
- 反复退出或重投撤销消息不会重新启用订阅或播放；普通会话到期后既有 Push 订阅仍能接收本账号事件，点击详情则先重新登录。

---

## 六、第五阶段：运行和整链路交付

### 6.1 运行任务

1. 记录注册/登录限流、会话校验失败、数据库错误、outbox 积压与投递重试指标，并以 `request_id` 串联请求；审计记录不包含秘密值。
2. 定期清理已过期会话和已完成投递的 outbox，保留必要审计；数据库恢复后会话状态与 outbox 一致，未完成通知继续投递。
3. 完成与 Vue 登录/注册/账号页、Nginx、device/event/media/push 服务的身份合同联调；前端遇 401 返回登录页并保留安全的站内目标路径。

### 6.2 最终交付物与验收

- 源码、数据库迁移、可运行镜像、接口说明、Nginx 配置、机密配置清单和恢复步骤。
- 可复现记录覆盖注册、登录、刷新恢复、退出、改密、会话超时、CSRF、伪造身份头、跨账号访问及撤销事件重投。
- 首发仅做个人账号登录与数据归属；不出现邀请成员、角色授权或共享数据入口。
